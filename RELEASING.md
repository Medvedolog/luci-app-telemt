# Как выпускается релиз

Пакет собирается **owfeed** вместо nfpm. Что это меняет по существу:

| | было (nfpm) | стало (owfeed) |
|---|---|---|
| `.apk` | Alpine apk **v2** | APK**v3**/ADB — формат, который реально использует apk-tools 3 в OpenWrt 25.12 |
| Подпись пакета | нет | EC-подпись автора **внутри** `.apk` |
| Подпись релиза | нет | `manifest.txt` + usign-подпись к нему |
| Версия | статичное поле в `nfpm.yaml`, которое CI переписывал через `sed` | тег |
| `/etc/config/telemt` | `type: config` | `conffiles:` — то же самое, проверяется в CI |
| Проверки | нет | Lua, JSON, шелл, содержимое пакета, `owfeed doctor`, установка на настоящий роутер |

Ничего из того, что попадает на роутер, не поменялось: те же файлы, те же зависимости,
те же три хука.

## Один раз: два ключа

**Это единственный шаг, который нельзя переложить на CI.** Подпись имеет смысл только
когда фид один раз закрепил у себя публичную половину и все последующие релизы
проверяются по ней же. Ключ, который CI создаёт и выбрасывает в конце задания,
закреплять не за чем — поэтому ключ создаёт человек, один раз, у себя.

Одна команда делает всё: создаёт оба ключа и кладёт их в секреты GitHub.

```sh
./tools/setup-keys.sh
```

Нужен [`gh`](https://cli.github.com), залогиненный с доступом к репозиторию. `owfeed`
скрипт скачает сам, если его нет.

| Ключ | Что подписывает | Зачем |
|---|---|---|
| `telemt-sign.pem` (EC prime256v1) | сам `.apk`, подпись лежит **внутри** файла | по ней кто угодно проверит, что пакет собрали вы, ничего не зная про фид, который его раздаёт |
| `telemt-release.key` (usign) | `manifest.txt` — опись релиза с размерами и sha256 | usign умеет проверять любой роутер OpenWrt «из коробки»; opkg на 24.10 отдельный `.ipk` проверить вообще не умеет |

Появятся секреты `TELEMT_SIGN_KEY` и `TELEMT_USIGN_KEY`.

> **Сохраните приватные половины (`.pem` и `.key`) в менеджер паролей до того, как
> закроете терминал.** Секрет из GitHub обратно не читается, отозвать ключ нельзя.
> Потеряли ключ — фид, уже закрепивший публичную половину, перестанет принимать
> релизы, пока человек вручную не закрепит новый.
>
> После этого папку `keys-setup/` удалите.

Руками, если не хочется скриптом:

```sh
owfeed keygen -o telemt-sign.pem
owfeed keygen -usign -o telemt-release.key
gh secret set TELEMT_SIGN_KEY  --repo Medvedolog/luci-app-telemt < telemt-sign.pem
gh secret set TELEMT_USIGN_KEY --repo Medvedolog/luci-app-telemt < telemt-release.key
```

## Каждый релиз

```sh
# 1. поднять версию на странице LuCI (usr/lib/lua/luci/model/cbi/telemt.lua)
#    CI и tools/stage.sh падают, если она разойдётся с тегом
git commit -am "Bump to 3.4.1" && git push

# 2. поставить тег — дальше всё делает CI
git tag 3.4.1
git push origin 3.4.1
```

Теги `3.4.1` и `v3.4.1` работают одинаково. Старый формат с ревизией (`v3.1.3-1`) тоже
понимается: `tools/stage.sh` превращает его в `3.1.3-r1`, потому что APKv3 принимает
после версии только суффикс `-r<число>` и ничего другого.

> Старый воркфлоу срабатывал на теги `3.3.*` и `[4-9]*` — под это `3.4.0` не подходил,
> и текущий релиз пришлось выпускать вручную через workflow_dispatch. Теперь ловятся
> все теги, начинающиеся с цифры или с `v`.

Что появится на странице релиза:

```
luci-app-telemt-3.4.1-r1.apk        OpenWrt 25.12 и новее
luci-app-telemt-3.4.1-r1.apk.sig
luci-app-telemt_3.4.1-r1_all.ipk    OpenWrt 24.10 и старее
luci-app-telemt_3.4.1-r1_all.ipk.sig
manifest.txt                        опись релиза: имена, размеры, sha256
manifest.txt.sig
```

`-r1` — ревизия сборки пакета, её требует APKv3. Поднимают её вручную только если
поменялся сам пакет, а приложение — нет: `./tools/stage.sh 3.4.1-r2`.

### Если релиз упал

Почините причину, удалите тег и поставьте заново — пайплайн идёт от тега:

```sh
git tag -d 3.4.1 && git push origin :refs/tags/3.4.1
git tag 3.4.1 && git push origin 3.4.1
```

Пересборка из того же коммита безопасна — `SOURCE_DATE_EPOCH` берётся
из времени коммита, поэтому пакет получается байт-в-байт тот же.

## Что проверяется до релиза

Всё это гоняется и на pull request, и ещё раз перед публикацией
(`.github/workflows/ci.yml`):

- **Lua 5.1** парсит `usr/**/*.lua`. Синтаксическая ошибка в CBI-модели на роутере
  выглядит как пустая страница, и единственный след — строчка в логе rpcd;
- **JSON** в `menu.d` и `acl.d` разбирается. Оба падают молча: пункт меню просто не
  появляется, а все RPC со страницы отклоняются;
- **шелл**: `dash -n`, `bash -n` и `shellcheck -S error` по `scripts/` и `tools/`;
- **CRLF и BOM** в хуках. Любое из двух — и OpenWrt `sh` не запускает скрипт вообще:
  из-за `\r` интерпретатором становится `/bin/sh\r`, а BOM перед `#!` превращает
  шебанг в обычную строку. `tools/stage.sh` их вычищает при сборке, но CI ещё и
  сообщает — прежний воркфлоу молча прогонял `dos2unix` и ничего не говорил;
- **`owfeed plan`** печатает, что будет собрано, до того как оно собрано: версия,
  имена файлов на обеих линиях, зависимости, conffiles;
- **`owfeed check`** — сборка, подпись, индекс и `doctor` на ключах, которые owfeed
  создаёт в этом же прогоне и выбрасывает. 714 проверок. Важнее всего `conffiles`:
  `/etc/config/telemt` без объявления пакетный менеджер считает своим файлом и при
  каждом обновлении затирает настройки прокси дефолтами, молча и с рапортом об успехе.
  Сюда же входят JSON и шелл **в payload** — то есть в дереве, которое реально
  уезжает на роутер, а не в исходниках;
- **содержимое собранного `.ipk`**: пять файлов на месте, `conffiles` объявлен,
  зависимости те самые (`luci-compat` теряется легче всего, а без него страница CBI
  отдаёт 500 на 23.05+), все три хука доехали и исполняемые;
- **пакет ставится на настоящий роутер** — owlab поднимает OpenWrt 25.12.5 и 24.10.8,
  ставит пакет, логинится в LuCI и открывает страницу приложения. Логин обязателен:
  неавторизованный запрос под `/cgi-bin/luci/admin` — это редирект на форму входа,
  поэтому обычный `curl` рапортует 403 на совершенно здоровой странице. Релиз идёт
  только после этого: `release: needs: [build, verify]`.

Секретов в этом workflow нет намеренно: он запускается на pull request, то есть на
коде из форков, и настоящий ключ в этой области видимости был бы ключом, на который
любой форк может направить работу.

## Собрать пакет у себя

```sh
./tools/stage.sh 3.4.1
owfeed build
ls dist/noarch dist/all
```

Подпись не нужна — ключи есть только у CI. На тестовый роутер:

```sh
scp dist/noarch/luci-app-telemt-*.apk root@192.168.1.1:/tmp/
ssh root@192.168.1.1 'apk add --allow-untrusted /tmp/luci-app-telemt-*.apk'
```

`--allow-untrusted` — потому что пакет ставится файлом, а не из подписанного индекса.

> Для проверки — нормально; как способ установки — нет. `apk add ./файл.apk`
> записывает в `/etc/apk/world` привязку к хешу файла, она переживает sysupgrade, и
> такой пакет больше никогда не обновится из фида.

## Чтобы пакет попал в общий фид

[owfeed-packages](https://github.com/owfeed/owfeed-packages) раздаёт пакеты
сообщества. После включения установка на роутере станет такой:

```sh
wget -qO- https://repo.owfeed.org/subscribe.sh | sh
apk add luci-app-telemt
```

Фид **ничего не собирает**: он берёт то, что вы собрали и подписали, проверяет вашу
подпись по закреплённому у себя ключу и подписывает свой индекс. Ваша подпись не
срезается — блоки подписей в apk складываются, и на роутер приезжает пакет с обеими.
Ключ фида вы не получаете, токен на ваш репозиторий фид не получает.

### Сначала — лицензия

**Это единственное, что сейчас блокирует подачу.** В репозитории нет файла `LICENSE`
и нигде не сказано, на каких условиях распространяется код. Репозиторий без лицензии
формально не разрешает никому его распространять, каким бы публичным он ни был — а
фид именно распространяет, и это второй акт распространения, который лицензия должна
разрешать.

Поэтому:

1. добавьте `LICENSE` (какую — решать вам; для LuCI-приложений обычно MIT, Apache-2.0
   или GPL-2.0, как у самой LuCI);
2. впишите тот же SPDX-идентификатор в `owfeed.yml` — там оставлено место с
   объяснением, поле называется `license:`. Оно попадает в индекс и в то, что
   показывает `apk info` на роутере.

В `owfeed.yml` лицензия сейчас не указана намеренно: выдумывать за автора разрешение,
которого он не давал, нельзя.

### Потом — заявка

Выпустите хотя бы один релиз по инструкции выше и заведите issue:

<https://github.com/owfeed/owfeed-packages/issues/new?template=package-request.yml>

| Поле | Значение |
|---|---|
| Repository | `Medvedolog/luci-app-telemt` |
| Release tag to check | тег вашего релиза, например `3.4.1` |
| What the release publishes | **manifest** — packages plus a signed manifest.txt |
| Manifest URL | `https://github.com/Medvedolog/luci-app-telemt/releases/latest/download/manifest.txt` |
| usign public key | содержимое `telemt-release.pub` целиком, обе строки |
| Key id | 16 hex-символов, печатается при `owfeed release` |
| Architectures | `noarch` |
| Release lines | отметить обе: 25.12 (apk) и 24.10 (ipk) |
| Licence | тот SPDX, который вы выбрали |
| Where the sources are | `https://github.com/Medvedolog/luci-app-telemt` |

Публичную половину EC-ключа (`telemt-sign.pub.pem`) приложите комментарием к тому же
issue — фид закрепляет её, чтобы подпись внутри `.apk` можно было проверить.

Перед подачей читают
[CONTRIBUTING_ru.md](https://github.com/owfeed/owfeed-packages/blob/main/CONTRIBUTING_ru.md)
и [LEGAL_ru.md](https://github.com/owfeed/owfeed-packages/blob/main/LEGAL_ru.md).
Коротко: фид раздаёт, но не проверяет содержимое, и ответственность за пакет остаётся
на авторе.

Дальше обновления идут сами: раз в час фид смотрит, не вышел ли новый релиз, проверяет
подпись манифеста и открывает у себя PR.
